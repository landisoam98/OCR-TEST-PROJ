# Read the text first, then ask the model

As of November 2026, the best fit for an 8-core, 32 GB, GPU-less Windows server reading scanned delivery notes is **not a single model but a two-stage pipeline**. Stage 1 runs classic OCR on every page: **RapidOCR 3.9.x with PaddleOCR's PP-OCRv6 models** on ONNX Runtime or OpenVINO. Stage 2 pulls the three fields out of that text with anchor-keyword rules plus a small text LLM (**Qwen3.5-4B, or 2B if speed matters, through llama.cpp with thinking off and a JSON schema**). A document VLM, **GLM-OCR (0.9B, MIT)** or **Qwen3-VL-4B / Qianfan-OCR**, is kept as a second opinion that runs only on pages the first pass can't settle. This design wins on CPU for three reasons. It is the only path with measured CPU speed in the low seconds per page. It runs natively on Windows through `pip` and a llama.cpp binary, with no WSL, Docker or vLLM. And it makes the tool's existing human-review folder far more effective, because every extracted value can be checked against text the OCR actually saw. The OCR-VLMs that top 2026 leaderboards (PaddleOCR-VL-1.6, GLM-OCR, MinerU's VLM) are GPU-first: **no one has published a measured seconds-per-page figure for any of them on an x86 8-core CPU**, and the few CPU runs that exist range from minutes per document to 531 s for one PaddleOCR-VL invoice page. InternVL, the company's previous model, has not shipped anything newer than 3.5 (August 2025), and its 3.5 release has only unofficial llama.cpp builds, so it belongs in the bake-off as a baseline, not as the default. Every speed and accuracy estimate below needs to be confirmed on the company's own 20-50 scans. A local bake-off is the deciding step, not a formality.

A note on evidence: Reddit could not be accessed directly (fetches failed, and `site:reddit.com` searches returned no threads), so community evidence here comes from GitHub issues, Hacker News, forums, blogs and small public benchmarks. Numbers are labelled **measured** (someone timed or scored a stated run), **vendor** (the model author's claim) or **estimated** (derived by the research team from component measurements).

## Only classic OCR has measured CPU speed in single-digit seconds

The central fact for this hardware is that CPU speed data is scarce, and what exists splits the options into two tiers that differ by one to two orders of magnitude.

Classic OCR has real numbers. PaddleOCR's own benchmark of the **PP-OCRv6 small** tier (released 11 June 2026) shows **0.59 s per image on OpenVINO and 0.61 s on ONNX Runtime** on an Intel Xeon 8350C, with the more accurate **medium tier at 1.40 s on OpenVINO** (measured, but by the vendor, on a 32-core server part with thread count unstated) ([PP-OCRv6 docs](https://www.paddleocr.ai/v3.7.0/en/version3.x/algorithm/PP-OCRv6/PP-OCRv6.html)). Independent runs are slower and show a real pitfall. On a 4-vCPU AWS instance, PP-OCRv6 small took **6.98-8.87 s per invoice** through the native PaddleOCR package, and going from 2 to 4 vCPUs saved only about 0.2 s because CPU use stalled near one core (measured) ([PaddleOCR #18320](https://github.com/PaddlePaddle/PaddleOCR/issues/18320)). An earlier Windows 11 CPU report put classic PaddleOCR 3.2 at about 60 s for a large TIFF page (measured, 2025) ([PaddleOCR #16610](https://github.com/PaddlePaddle/PaddleOCR/discussions/16610)). The lesson is to use the ONNX/OpenVINO route through RapidOCR rather than native Paddle, and to get throughput from several parallel worker processes rather than one process with many threads. **RapidOCR 3.9.0 made PP-OCRv6 small its default** and installs with `pip install rapidocr onnxruntime` under Apache-2.0 ([RapidOCR v3.9.0](https://newreleases.io/project/github/RapidAI/RapidOCR/release/v3.9.0), [RapidOCR GitHub](https://github.com/RapidAI/RapidOCR)). On a no-AVX Celeron, native PaddleOCR crashed with "Illegal instruction" while RapidOCR ran fine (measured) ([dev.to](https://dev.to/ganesh-kumar/how-a-tiny-ocr-model-finds-reads-and-orders-text-on-a-page-without-a-gpu-kk9)). Tesseract is faster still, at about **0.27-0.67 s/page** ([joshua8.ai](https://joshua8.ai/ocr-models-vs-vision-llms-vs-tesseract/), [imagetotable.ai](https://imagetotable.ai/references/ocr-latency-benchmark)), but loses badly on accuracy (next section).

The text LLM step also has component measurements. On a 16-core EPYC with 8 generation threads, **Qwen3.5-4B Q4 generated 8.5 tokens/s and Qwen3.5-2B 18.4 tokens/s** with thinking off (measured) ([igllama](https://bkataru.github.io/igllama/showcase/qwen35-small/)). A separate llama-bench run had Qwen3-4B Q4_K_M at 6.5 tokens/s decode (measured, on a possibly bandwidth-limited machine) ([b4ph bench](https://huggingface.co/b4ph/qwen3-4b-lowram-bench)). A three-field JSON answer is about 40-80 tokens, so the research team **estimates 10-25 s per page end to end for OCR plus a 4B model, and 5-10 s with a 2B model**. That is an estimate composed from parts, not a measured pipeline. On an i7-8700, llama.cpp peaked at 8 threads and slowed with all 12 logical threads, so `-t 8` (physical cores) is the starting point (measured) ([InventiveHQ](https://inventivehq.com/blog/cpu-thread-scaling-llm-inference)).

VLMs on CPU have almost no clean numbers. The few that exist:

The Transformers FP32 path is unusable; the decisive levers are runtime and image size. OpenVINO cut SmolVLM2-256M end-to-end latency from 25.9 s to 0.74 s versus PyTorch on a Core Ultra 7 (measured, tiny model and image) ([HF blog](https://huggingface.co/blog/openvino-vlm)), and gave 8.49x on Qwen2.5-VL-7B INT4 on a 48-core Xeon 6 ([Lenovo Press](https://lenovopress.lenovo.com/lp2305-accelerating-multimodal-llms-on-intel-xeon-6-processors-using-openvino)). Through llama.cpp at Q4/Q8 with the page downscaled to about 1 megapixel, the research team **estimates 10-60 s/page for a 0.9B OCR-VLM and 30-90 s/page for a 2-4B general VLM** on 8 cores. Those ranges fit a 30-90 s budget but are unverified. Even the pessimistic case is affordable at this volume: 300 pages at 90 s is 7.5 hours, an overnight queue. Speed therefore rules nothing out; it decides what runs on every page versus only on hard pages.

## Leaderboard winners are page-to-markdown parsers, not field extractors

The 2026 document-VLM leaderboards measure full-page parsing (OmniDocBench, olmOCR-bench), which is a different job from "find the DN number". **PaddleOCR-VL-1.6** (0.9B, Apache-2.0) scores 96.3 on OmniDocBench v1.6 and its 1.5 paper explicitly targets skewed, warped and noisy scans ([PaddleOCR-VL docs](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PaddleOCR-VL.html), [arXiv 2601.21957](https://arxiv.org/html/2601.21957v1)). But its prompts are fixed (`OCR:`, `Table Recognition:` and similar), with no documented key-information mode, so you still need rules or an LLM afterwards ([PaddleOCR-VL-1.5-GGUF](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.5-GGUF)). **GLM-OCR** (0.9B, MIT, OmniDocBench v1.5 94.62) is the only small OCR-VLM whose card documents **prompted extraction into a strict JSON schema**, but its "state-of-the-art" extraction claim comes with no number ([zai-org/GLM-OCR](https://huggingface.co/zai-org/GLM-OCR)). **MinerU**, Granite-Docling and LightOnOCR are markdown converters. MinerU's CPU `pipeline` backend is officially supported on Windows, but it changed in April 2026 to a custom "MinerU Open Source License" that needs review, and Windows users report 260-character path failures and a Python 3.10-3.12 requirement ([MinerU changelog](https://opendatalab.github.io/MinerU/reference/changelog/), [Windows setup guide](https://github.com/gaoyuindeu/mineru-windows-setup-guide)). None of these publish form or invoice extraction scores (FUNSD, SROIE, CORD) in the 2026 sources.

General small VLMs do report extraction scores, all vendor-reported. On Baidu's comparison, **Qianfan-OCR (4B, Apache-2.0) scores 87.9 overall on key-information extraction versus 83.5 for Qwen3-VL-4B**, which is within a point of the 235B flagship. That suggests 8-9B models buy little for three header fields ([Qianfan-OCR GGUF card](https://huggingface.co/Mungert/Qianfan-OCR-GGUF)). **Qwen3.5-4B** (Apache-2.0, Feb-Mar 2026) reports OCRBench 85.0 and OmniDocBench1.5 86.2, slightly below Qwen3-VL-4B's OCRBench 873 ([Qwen3.5-4B card](https://huggingface.co/Qwen/Qwen3.5-4B)). **Gemma 4 E4B** (Apache-2.0) lets you set the image token budget (280-1120 recommended for documents), which is useful for capping CPU cost, but reports no DocVQA or OCRBench score ([gemma-4-E4B-it](https://huggingface.co/google/gemma-4-E4B-it)).

The question that matters is whether OCR text plus an LLM loses accuracy against a VLM reading the image. The evidence splits by document quality. On SROIE receipt header fields, the closest public analog to a DN header, Qwen2.5-7B reading **PaddleOCR text found the right field 99.4% of the time (key recall), but exact match fell from 0.687 on perfect text to 0.574**. Gemma 2B dropped to 0.385 exact match. PaddleOCR beat EasyOCR and Tesseract downstream by a wide margin, with Tesseract collapsing on dense receipts (CORD value F1 0.149 against PaddleOCR's 0.491) (measured) ([Pixels to Pairs, arXiv 2609.17538](https://arxiv.org/pdf/2609.17538)). A small public benchmark is the most relevant head-to-head. On 100 clean invoices with unseen layouts, **RapidOCR + qwen2.5:7b scored field F1 0.922 against 0.964 for two-shot qwen3-vl:8b**. On 100 photographed receipts, though, **OCR + LLM collapsed to 0.336 against 0.680** for the VLM (measured, on a GPU) ([vlm-document-extraction](https://github.com/Tajaddin/vlm-document-extraction)). SAP's study of about 1,000 real supply-chain documents, with a delivery note as the prompt example, found image-only and OCR-only input roughly equal for large cloud models, and OCR-only scores rising from 57% to 74% with model size (measured) ([arXiv 2603.02789](https://arxiv.org/html/2603.02789)). In short: on printer-scanned, mostly typed pages, OCR plus a small LLM comes within a few points of a VLM at a fraction of the CPU cost. On genuinely degraded pages, the VLM recovers what the OCR lost. That is exactly why the VLM belongs in the fallback slot.

Language coverage favours PP-OCRv6. Its medium and small tiers read Simplified and Traditional Chinese, English and 46 Latin-script languages in one model ([PP-OCRv6 docs](https://www.paddleocr.ai/v3.7.0/en/version3.x/algorithm/PP-OCRv6/PP-OCRv6.html)). Malay is not named in the list, so its support is inferred from the Latin alphabet; for DN numbers, dates and names, the character set matters more than the language. No source tested any pipeline on Malay or Chinese delivery notes.

## Failure modes are invention, looping and silent date swaps

The documented failures argue against trusting any generative model unchecked. **Invention** is the most dangerous. A paperless-gpt user who had mistakenly configured a text-only model as the vision model got weeks of fabricated but plausible German receipts ("Rechnung Nr. 2024-0847", "Mustermann GmbH"), and local runtimes gave no error ([woitzik.dev](https://woitzik.dev/blog/llm-hallucinated-ocr-paperless/)). Gemini has been observed making up a plausible invoice number when none was on the page, while a fine-tuned Qwen3-VL-4B tended to omit fields instead ([arXiv 2605.22413](https://arxiv.org/pdf/2605.22413)). **Repetition loops** affect Qwen3-VL from 2B to 32B during OCR across transformers, llama.cpp, Ollama and LM Studio, and the issue remains open ([Qwen3-VL #1611](https://github.com/QwenLM/Qwen3-VL/issues/1611)). GLM-OCR on CPU Ollama repeats endlessly without a stop sequence, and sometimes even with one ([GLM-OCR #220](https://github.com/zai-org/GLM-OCR/issues/220)). **Configuration traps** include Ollama's default context truncating image tokens and thinking-capable models returning empty output ([Level1Techs](https://forum.level1techs.com/t/need-help-with-ai-ocr-for-paperless-ngx/249465), [paperless-gpt #1201](https://github.com/icereed/paperless-gpt/issues/1201)). **Date errors** are mundane but common: one Odoo OCR module silently parsed US 09/04/2026 as 9 April, and an LLM-returned 30 February crashed the whole result ([odoo-ocr-ai #16](https://github.com/molnkontakt/odoo-ocr-ai/issues/16)).

Two lessons matter for this tool. First, asking for **three short JSON fields instead of a full-page transcription** shrinks exposure to loops and invention, and a hard `max_tokens` cap with temperature 0 bounds the rest ([ggml OCR guide](https://huggingface.co/blog/ggml-org/using-ocr-models-with-llama-cpp)). Second, a model's own confidence flags are weak: in the public invoice benchmark, **review flags caught only a third to half of the wrong documents** ([vlm-document-extraction](https://github.com/Tajaddin/vlm-document-extraction)). The checks that catch errors must be external and deterministic.

The safety checks that fit the existing tool's design (route unclear results to the review folder, validate dates) are these, each a hard gate. **Grounding**: every extracted value must appear verbatim or by tight fuzzy match in the classic OCR text, the LMDX technique that discards hallucinated values by design ([LMDX, arXiv 2309.10952](https://arxiv.org/abs/2309.10952)). A DN number the OCR never saw goes to review, whichever model produced it. **Format**: the DN number must match a known pattern (the company's own DN prefixes, or per-supplier patterns learned from the bake-off). **Customer match**: there is no customer master list, so the tool's self-built list (existing customer folders plus `customers.json`) plays that role. A name that matches a known customer is filed under that folder's name, not the raw OCR string. A new name that is close to, but not the same as, a known one goes to review instead of creating a near-duplicate folder. **Date plausibility**: parse as DD/MM/YYYY (the Malaysian convention), keep the raw string alongside the ISO value, reject impossible or future dates and dates outside a window around the scan date, and send to review any date where day and month are both 12 or under and the layout's convention is unknown ([pdfvector](https://www.pdfvector.com/blog/validate-extracted-data-from-invoices)). **Agreement**: when the VLM fallback runs, auto-file only if it agrees with the rules or LLM result on all three fields. **Canary**: a fixed known page runs at service start and must return its known values, which catches a wrong model, broken vision input or a silent runtime change. One page per request, temperature 0, a stop sequence and a `max_tokens` cap of about 150 round it out.

## Windows support and licences narrow the field to llama.cpp, ONNX and Apache/MIT

Native Windows deployment rules out most fast paths. vLLM, SGLang and FastDeploy, the default fast backends for PaddleOCR-VL, dots.mocr, olmOCR and Chandra, do not run natively on Windows, and PaddleOCR-VL's official Docker image is NVIDIA-only ([PaddleOCR-VL docs](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PaddleOCR-VL.html)). The clean route is **llama.cpp installed with `winget`**, which serves GLM-OCR, PaddleOCR-VL, Qianfan-OCR, Qwen3-VL, Qwen3.5 and Gemma 4 GGUFs behind an OpenAI-style endpoint ([PaddleOCR-VL-1.5-GGUF](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.5-GGUF), [ggml OCR guide](https://huggingface.co/blog/ggml-org/using-ocr-models-with-llama-cpp), [Qwen3-VL GGUF](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct-GGUF)). Known Windows bugs exist: PaddleOCR with the llama.cpp server returned HTTP 500 on images containing curly quotes ([PaddleOCR #18170](https://github.com/PaddlePaddle/PaddleOCR/issues/18170)), and Ollama GGUFs tagged `glmocr` don't load in stock llama.cpp ([llama.cpp #19335](https://github.com/ggml-org/llama.cpp/issues/19335)). Pin a llama.cpp build that passes the bake-off.

InternVL is the awkward one. llama.cpp officially supports **InternVL 2.5 and 3**. InternVL3.5 exists only as third-party GGUF conversions, one labelled a "test" ([llama.cpp multimodal docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md), [QuantStack](https://huggingface.co/QuantStack/InternVL3_5-2B-gguf/blob/main/README.md)). Its tiling also costs CPU time: 256 tokens per 448-pixel tile with up to 12 tiles means up to about 3,300 image tokens per page ([InternVL3.5-4B card](https://huggingface.co/OpenGVLab/InternVL3_5-4B)), against roughly 1,000-2,000 for Qwen at about 1 megapixel (estimated) or a fixed 280-1,120 for Gemma 4. Its licence (Apache-2.0) is not the problem; tooling momentum has moved to Qwen and Gemma.

## The recommended pipeline and a bake-off that decides it

**Recommendation.** Rasterise each PDF page at about 200-300 DPI (pypdfium2), deskew with OpenCV, and run RapidOCR with PP-OCRv6 (start with small; switch to medium if faint scans fail). Keep the OCR lines with their box coordinates. First try anchor-keyword rules ("DO No", "D/O No", "DN No", "Delivery Order", "Date", "Tarikh", "Customer", "Bill To", "Deliver To", plus Chinese equivalents such as 送货单 and 日期), searching near each anchor's box. If rules don't yield all three fields cleanly, send the OCR lines in reading order with compact coordinates to **Qwen3.5-4B Q4_K_M** in llama.cpp with thinking off, temperature 0, a JSON schema and one or two examples. Run every result through the hard gates above. Only pages that fail a gate go to the VLM (GLM-OCR or Qwen3-VL-4B, whichever wins the bake-off), using a header crop or a page capped near 1 megapixel. That page auto-files only if the VLM's values also pass grounding and agree with the stage-2 values; anything else goes to the review folder. Run two to four worker processes rather than one large one.

**Bake-off on 20-50 of the company's own scans.** Choose pages deliberately: the main customers' layouts, at least five faint or skewed scans, any with Chinese or Malay text, multi-page PDFs, pages with several dates (order date, delivery date, print date), and any page that defeated InternVL. Hand-label the correct date, canonical customer name and DN number for each. Run every candidate on identical pages: (1) RapidOCR v6 small + rules only; (2) + Qwen3.5-4B; (3) + Qwen3.5-2B; (4) PP-OCRv6 medium in place of small; (5) GLM-OCR JSON mode alone; (6) Qwen3-VL-4B or Qianfan-OCR alone; (7) PaddleOCR-VL-1.6 `OCR:` + rules; (8) InternVL3-2B as the continuity baseline. Optionally add Gemma 4 E4B at an image budget of 560. Then run the full cascade (1 → 2 → VLM fallback with gates).

Record, per configuration: per-field exact match; whole-document all-three-correct; the **auto-file rate** (share passing all gates); the **wrong-auto-file count** (pages that passed every gate yet were wrong, the only error that costs real money because nobody looks); warm seconds per page, cold start and peak RAM on the actual server. The acceptance rule is **zero wrong auto-files, then the highest auto-file rate within the time budget**. Be honest about what a small sample proves: zero errors in 50 pages still allows a true wrong-file rate of up to about 6% at 95% confidence (the "rule of three", 3/50). So keep logging after go-live, sample-audit a few auto-filed PDFs each week, and add every reviewed page to the test set. If a layout keeps failing zero-shot, the CENTURIA study found a LoRA on 57 labelled samples lifted field accuracy above 87% from under 3% on unusual forms ([arXiv 2608.30616](https://arxiv.org/abs/2608.30616)). That fine-tuning needs a GPU elsewhere, but the result runs on this CPU as a GGUF.

## Conclusion

The research reframes the choice. The question was "which model replaces InternVL", but on a CPU-only server the model matters less than the architecture around it. Generative readers, large or small, fail by producing confident text that isn't on the page, and their self-reported confidence catches only part of it. A cheap deterministic OCR layer turns every extraction into something checkable. That makes the existing review folder a precise safety net instead of a dumping ground, and it confines the slow VLM to the minority of pages that need it. The biggest risk is not accuracy on clean pages, where the options are within a few points of each other; it is an undetected wrong filing. That is why the bake-off should be scored on wrong auto-files, not average accuracy.

The evidence base is thin in precisely the places that matter here. There is no measured x86 CPU timing for any 2026 OCR-VLM, no delivery-note benchmark, no Malay or Chinese DN test, and no Reddit consensus to lean on. The vendor leaderboards will keep moving (HunyuanOCR-1.5, OvisOCR2 and OCRia-1 all appeared in 2026 with unclear licences or no CPU data), so the most durable asset the company can build is not a model choice but its own labelled 50-page test set and gate logic. Those let any future model be swapped in and judged in an afternoon.
